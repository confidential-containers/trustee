# SPIRE Delegated Identity Plugin

This plugin allows Trustee to collaborate with an existing SPIRE agent/server
to provide SVIDs to confidential workloads.
Specifically, this plugin uses the SPIRE Agent's Delegated Identity API, which takes a list
or selectors and returns an SVID.
This plugin parses these selectors from the Validated Identifiers field in the attestation token
and returns the SVID to the VM as an encrypted resource.
The plugin also provides trust bundles.

At a high-level, the goal of confidential SPIRE is to provide an SVID that is backed by cryptographic
guarantees.
In other words, the properties represented by the SPIFF-ID, must reflect the workload that is
actually running inside the enclave, and there should be cryptographic evidence of this.

These guarantees are achieved through an abstraction called Validated Identifiers.
Validated Identifiers are an extension of the Trustee attestation token that contain
provable properties of the guest.
Validated Identifiers are extracted from the hardware evidence and Init-Data plaintext
by the attestation policy.
The validity of these identifiers depends on a number of components.

With Confidential Containers, most validated identifiers are rooted in the Kata Agent policy,
since this defines which workloads can run inside a podvm. 
First, the Kata Agent policy is generated before boot.
This defines what the pod will look like.
The Kata Agent Policy is added to the Init-Data, which is measured at boot-time.
This binds a podvm to a pod definition.
When a workload requests an SVID from Trustee, the attestation policy determines
the TCB status and extracts Validated Identifiers from the Init-Data.
This plugin then formats the identifiers as selectors and passes them to the SPIRE Agent.

Note that the plugin does not confirm the TCB status. A KBS policy should be used
to check that the TCB status is affirming.
If the overall TCB status of the guest isn't checked,
there is no way to know if the podvm honored the Kata Agent Policy.
Thus, the Validated Identifiers would not be trustworthy.

You can use this plugin with other runtimes as well, as long as you adjust
the attestation policy to extract the necessary Validated Identifiers.
Make sure that the runtime itself respects these identifiers.

This plugin collects selectors at the granularity of the podvm.
In Kubernetes terms this means that it can only generate pod-level selectors.

The plugin can be configured to create selectors that look the same as
selectors that would be generated by the SPIRE k8s workload attestor,
so that a workload can be transparently run inside of CoCo using existing
workload entries.
On the other hand, the plugin can also explicitly denote that the selectors
are generated by Trustee. See configuration options below.

## Configuration

|----------------------------|--------|------------------------------------------------------------------------------------|-----------|
| `admin_socket_path`       | String | Filesystem path to the SPIRE Agent's admin (Delegated Identity API) Unix socket    | -         |
| `attested_selector_value` | String | Value used for the always-added `trustee:<value>` marker selector                  | `true`    |
| `k8s_selector_prefix`     | String | Selector type used for known k8s workload attestor selector keys                   | `k8s`     |
| `trustee_selector_prefix` | String | Selector type used for the marker selector and any other identifier key            | `trustee` |

Note that `admin_socket_path` should point to the SPIRE Agent admin UDS. This is not the same as workload API UDS
and usually needs to be enabled via the SPIRE Agent config file.

This plugin splits selectors into two groups; those that match the k8s workload attestor and those that do not.
The prefix/type of these two groups can be set independently.
By default, selectors that match those that the k8s workload attestor might create, will use the same type
that SPIRE would use.
Other selectors will use the prefix `trustee`.
Additionally, one selector will always be added to specify that the selectors were generated by Trustee. 
The value of this selector is configurable, allowing you to emit a selector that is specific 
to your Trustee instance.

## Setup

To connect to the SPIRE Agent admin socket, this plugin itself needs an SVID.
Thus, there must be a SPIRE Agent that the KBS can attest with.
Depending on how Trustee is deployed you can use the k8s workload attestor
or the unix attestor for this.
In either case, you will need to create a workload entry reflecting Trustee.
You will also need to specify the SPIFFE-ID of this workload entry
as an `authorized_delegate` in the SPIRE Agent config file.

Note that the SPIRE Agent admin socket will automatically resolve connections to SPIFFE-IDs.
There is not need for the plugin to contact the workload API separately.

## Usage 

Once the plugin is configured, request an `x509-svid` resource from the SPIRE plugin.
This is identified by a resource URI such as `kbs+spire:///x509-svid`.
